# 効果は共通の Effect リストで表現する

## 背景

食事・イベント・制度の3機能は、どれも「選択肢を選ぶとステータスが動く」という同じ構造を持つ。一方で**数値も効果の種類も今後どんどん変わる／増える**ことが分かっている（例：高級な食事の効果を「Badイベントが減る」から「Goodイベントが増える」に変更、など）。

各機能がそれぞれ `GameState.I.AddStress(+5)` のような呼び出しを直接書くと、効果の種類を1つ足すたびに3人のコードを別々に直すことになる。誰かが直し忘れれば挙動がばらつく。

## 決定

**「何がどれだけ動くか」を `Effect` という共通のデータで表し、適用は1箇所（`EffectApplier`）にまとめる。**

食事のグレード・イベントの選択肢・制度は、それぞれ `List<Effect>` を持つだけにする。仕様は [../design/effects.md](../design/effects.md)。

効果の種類を足すときにやることは2つだけ：`EffectKind` に値を足す／`EffectApplier` に case を足す。これだけで3機能すべてが新しい効果を使えるようになる。

## 検討した他の案と、採らなかった理由

- **各機能が `GameState` を直接叩く（ハンドアウトの書き方）** … 最初の1機能を動かすには最短だが、効果の種類が増えるたびに3箇所を直すことになる。今回のように仕様が動く前提だと割に合わない。
- **効果ごとにクラスを作る（StressEffect, MoneyEffect …）** … 拡張はできるが、Inspector で編集しづらく、バランス調整のたびにクラスが増える。データとして並べたいので enum + 値の形を選んだ。

## 結果・影響

- 選択肢カードのチップ表示も `Effect` のリストから自動生成できる。効果を足したのに表示を書き忘れる、という事故が起きない。
- バランス調整がデータの書き換えだけで済む。数値をコードにハードコードしないという既存のルールとも一致する。
- **土台を誰が作るかを先に決める必要がある。** 3機能の共通部分なので Core 側（山口）が自然。これが無いうちは、各自ハンドアウトの書き方（`GameState` を直接叩く）で試作を進めてよいが、後で差し替える前提にしておくこと。
- 名前（`Effect` / `EffectKind` / `EffectApplier` / `Choice`）は仮。3人で使うので早めに確定したい。
