# カレンダーを開いている間はゲームの進行を止める

> ⚠ **この ADR は [0004-pause-during-decisions.md](0004-pause-during-decisions.md) に置き換わりました。** 判断は覆っていませんが、対象がカレンダー以外の画面（制度一覧・食事選択・イベントの行動選択）にも広がり、実装方法も「停止要求をカウントする」形に決まりました。現在有効なのは 0004 です。

## 背景

このゲームは1秒＝1日でリアルタイムに進む（[0001-realtime-time-model.md](0001-realtime-time-model.md)）。一方でカレンダー機能（[../design/calendar-system.md](../design/calendar-system.md)）は、申請期限を確認したりメモを書いたりと、**読んで考える時間が必要な画面**になる。

止めないまま開くと、プレイヤーが予定を読んでいる間に日が進み、確認しようとしていた締め切り自体が過ぎてしまう。「知っていれば得をする」というテーマなのに、知ろうとした行為が罰になる。

## 決定

**カレンダー画面を開いている間は、ゲームの進行を一時停止する。**

実装は `GameClock.SetRunning(false)` / 閉じたら `SetRunning(true)`。→ [../code/architecture.md](../code/architecture.md) 2章

## 検討した他の案と、採らなかった理由

- **止めない** … 読んでいる間に締め切りが過ぎる。確認するほど損をするので、テーマと矛盾する。
- **ゆっくりにする（減速）** … 「急がされている」感覚は残るが、メモを書く画面で急かされるのは単純に操作しづらい。

## 結果・影響

- 読む・書く操作が安心してできる。カレンダーが「確認しに来る場所」として機能する。
- 時間を止めても得をする抜け道は作らないこと。バランススライダーはいつでも調整できるが、止まっている間は日数が進まないので給与もストレスも動かない（[../code/architecture.md](../code/architecture.md) 4章）。
- **未決定**：同じく全画面で開く制度一覧（`supports`）など、他のモーダル画面も止めるか。止めるなら、複数の画面が同時に停止を要求したときのために、`SetRunning` を直接呼ぶのではなく**停止要求をカウントする仕組み**にしたほうが安全（片方を閉じた瞬間にもう片方が開いているのに動き出す事故を防ぐ）。
