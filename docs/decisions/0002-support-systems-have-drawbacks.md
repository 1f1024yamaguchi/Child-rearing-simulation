# 支援制度に必ずデメリットを持たせる

## 背景

このゲームのテーマは「子育てを助けてくれる制度・アプリを知ること」。しかし支援制度を「使えば得するだけのもの」として実装すると、プレイヤーは全部申請するだけになり、判断が生まれない。現実の制度にも自己負担・所得制限・キャリアへの影響といったコストが必ずある。

## 決定

- **すべての支援制度に、メリットとセットで現実のデメリット／自己負担を持たせる。**
- デメリットは制度ごとにバラバラに考えず、**7つの「型」**に落とす（申請の手間／自己負担／所得・条件で対象外／収入・キャリア低下／待機・定員・運／副作用／手続きの継続）。→ [../design/support-systems.md](../design/support-systems.md) 2.5章
- 制度一覧の UI では、メリット（緑）とデメリット（赤）を**必ず並べて表示**し、ノーリスクに見せない。

## 検討した他の案と、採らなかった理由

- **メリットのみ（申請すれば純粋に得）** … 全部申請するのが最適解になり、選択がゲームにならない。制度の現実も伝わらない。
- **制度ごとに個別のデメリットを自由に設定** … 数が増えたときにバランス調整が破綻する。型に落としたほうが実装も調整も楽。

## 結果・影響

- 「良い制度を、コストを払ってどう使うか」という判断ゲームになり、テーマ（制度を知る）とも一致する。
- 制度データは 7 つの型を持つ構造にする必要がある（実装時に enum などで表現）。
- イベント側（[../design/events.md](../design/events.md)）ともデメリット／メリットを連動させると深みが出る。例：予防接種の補助を受けておくと風邪イベントの確率が下がる。
